MBID Storage — Reality Check

Tracks are loaded from MediaStore, not Room. There's no existing "tracks" table to add columns to.

The Situation

Track is a domain model built from ContentResolver queries — metadata lives in audio file tags, not in a database table. The Room database currently stores only LovedTrackEntity and TrackStatsEntity.

Two Paths Forward

A

Audio file tags only — no Room

Write MBIDs to file tags via jaudiotagger FieldKey. Other tools read them. Lotus re-reads from tags when needed (v2.0 re-matching).

Pros

  • Zero database changes
  • No migration
  • Picard/beets/Plex see the IDs immediately

Cons

  • Can't query by MBID without re-reading files
  • No DB-level uniqueness for future features
B

New lightweight Room entity + file tags

Create TrackMetadataEntity(trackData, mbAlbumId?, mbReleaseGroupId?, mbAlbumArtistId?). Just 4 columns, keyed by track path.

Pros

  • Queryable by MBID without tag re-read
  • Ready for v2.0 AcoustID re-matching
  • Simple migration (new table, no data migration)

Cons

  • New entity + DAO + migration
  • More code to write and maintain

Recommendation

Option A (audio file tags only) is the right call for v1.8. We have zero features that need to query by MBID today. v2.0's AcoustID integration is the natural point to add a Room table — when we actually need to query against it. Adding a table now with no consumer is speculative infrastructure.

This is different from my earlier recommendation because I discovered Track isn't persisted in Room. The "Option B" I endorsed assumed existing DB infrastructure that doesn't exist.
