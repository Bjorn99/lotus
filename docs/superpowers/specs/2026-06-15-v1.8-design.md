## Group A — Independent improvements

### 1. WavingSeekBar tuning

**Problem:** Three changes shipped in v1.7.1 but none are perceptible:
- Static wave at `canvasHeight / 6f` (1dp) is invisible against a 3dp stroke
- Spring at `dampingRatio=0.6f, stiffness=400f` settles in ~80ms — faster than human visual perception (~150ms)
- When the infinite transition is destroyed on pause, `offset` snaps to 0, so the static wave isn't a freeze-frame of the playing wave

**Fix A — visible static wave:** Change `canvasHeight / 6f` to `canvasHeight / 3f` (2dp ripple on a 6dp bar). Visible but clearly different from the full-amplitude playing wave.

**Fix B — phase capture:** When the infinite transition is destroyed (playback pauses), capture the current `offset` value before it resets to 0. Store it in a `remember { mutableFloatStateOf(0f) }` that updates on each frame while playing and freezes on pause. The static wave renders using this frozen offset, so it looks like the wave just stopped moving — not like it reset to a different shape.

```kotlin
// In FilledSeekBarSegment:
var frozenOffset by remember { mutableFloatStateOf(0f) }
// The offset animation already runs; capture its value each frame:
LaunchedEffect(offset) {
    if (enableWaving) frozenOffset = offset
}
// When rendering the path, use:
val effectiveOffset = if (enableWaving) offset else frozenOffset
```

**Fix C — visible spring:** Change `dampingRatio` from 0.6f to 0.5f and `stiffness` from 400f to 300f. This gives one visible bounce cycle with ~200ms settle time — noticeable on any tap distance but not distracting.

### 2. Token-bucket rate limiter

**Problem:** The current `delay(1100)` before every MusicBrainz call wastes time even when the previous call was minutes ago. Two consecutive calls (search + cover art lookup) always cost 2.2 seconds minimum.

**Fix:** Replace with a coroutine-based token bucket (capacity 5 tokens, refill 1/sec). This matches MusicBrainz's documented rate limit policy and the ecosystem standard (Picard, beets, musicbrainz_rs).

```kotlin
// New file: app/src/main/java/com/dn0ne/player/core/util/RateLimiter.kt
class RateLimiter(capacity: Int = 5, refillPerSecond: Int = 1) {
    private val tokens = Channel<Unit>(capacity = capacity)

    init {
        // Pre-fill to capacity
        repeat(capacity) { tokens.trySend(Unit) }
    }

    // Refill loop runs as a coroutine
    suspend fun run(scope: CoroutineScope) {
        while (true) {
            delay(1000L / refillPerSecond)
            tokens.trySend(Unit)
        }
    }

    suspend fun acquire() { tokens.receive() }
}
```

Usage:
```kotlin
// In MusicBrainzMetadataProvider — replace delay(1100) with:
rateLimiter.acquire()
```

The refill coroutine is launched once in the provider's scope. Five calls in rapid succession burst through immediately, then the sixth call suspends until the next refill. This means search + cover art = instant if you haven't called recently, vs. 2.2 seconds today.

**No new dependencies.** Uses only `kotlinx.coroutines.channels.Channel`.

### 3. 503 retry with backoff

**Problem:** MusicBrainz returns HTTP 503 when the client exceeds the rate limit. The current code maps 503 to `DataError.Network.ServiceUnavailable` and gives up. A transient 503 should trigger a retry.

**Fix:** Configure Ktor's built-in `HttpRequestRetry` plugin on the MusicBrainz HttpClient. This is a plugin we install once in the Ktor client configuration — zero hand-rolled retry logic.

```kotlin
// In the Ktor HttpClient config for MusicBrainz:
install(HttpRequestRetry) {
    retryOnServerErrors(maxRetries = 2)
    retryOnException(maxRetries = 3, retryOnTimeout = true)
    exponentialDelay(
        base = 2.0,           // 2s, 4s, 8s...
        maxDelayMs = 60_000L,  // cap at 60s
        randomizationMs = 1000 // ±1s jitter to prevent thundering herd
    )
}
```

This handles both 503 (server error) and network exceptions (timeout, connection refused). The jitter prevents synchronized retry storms. Combined with the token bucket (item 2), the app self-throttles before hitting 503, and gracefully recovers if it does.

### 5. Inter font subsetting

**Problem:** Inter ships as 4 full TTF files (~400KB each, 1.6MB total). Inter covers the full Unicode range — Cyrillic, Greek, CJK, Arabic, Vietnamese — none of which Lotus uses. Music metadata is overwhelmingly Latin script.

**Fix:** Run `pyftsubset` (part of `fonttools`, Python) to subset each weight to the Latin-1 Supplement range (U+0000–U+00FF), plus common punctuation and symbols used in music metadata (en dash, em dash, bullet, ellipsis, smart quotes). This covers every character in any Western music library.

```bash
pip install fonttools brotli
pyftsubset Inter-Regular.ttf \
    --unicodes="U+0000-00FF,U+2010-201F,U+2022,U+2026,U+2032-U+2033" \
    --output-file=inter_regular.ttf \
    --flavor=woff2 \
    --no-hinting \
    --desubroutinize
# Repeat for Medium, SemiBold, Bold
```

The `--flavor=woff2` option uses Brotli compression (better than gzip). Android supports WOFF2 natively in the font resource system.

**Expected result:** ~50KB per weight, ~200KB total. Savings: ~1.4MB (26% of current APK).

**Verification:** Build release APK before and after, compare `resources.arsc` and font file sizes. Spot-check that track titles with accented characters (é, ñ, ü, ø) render correctly.

### 5a. Settings scroll jank fix

**Problem:** All settings sub-pages feel sluggish during scrolling. Root cause: `ColumnWithCollapsibleTopBar.onPreScroll`
subtracts `contentScrollState.value` (absolute scroll position) from a delta-based height formula, creating a
positive-feedback loop where more scrolling produces faster-than-finger top-bar collapse. Additionally,
`coroutineScope.launch { snapTo() }` fires per scroll frame, and `LaunchedEffect(topBarHeight.value)` cancels
and relaunches its coroutine on every value change during collapse animation. `SettingsItem` data class is unstable
due to lambda-backed `onClick` field causing unnecessary recomposition.

**Fix:**
- Replace `contentScrollState.value` subtraction with a pure delta-only `calculateTopBarHeight` function
- Gate `snapTo` behind a `newHeight != previousHeight` check so the coroutine only dispatches when the value changes
- Replace `LaunchedEffect(topBarHeight.value)` with `snapshotFlow` to avoid coroutine cancellation churn
- Annotate `SettingsItem` with `@Immutable` and extract `onClick` lambda as a separate composable parameter
- Simplify the LazyColumn variant's gating condition (remove `firstVisibleItemIndex >= 0` tautology)

**Expected result:** Smooth 60fps scrolling in all settings pages, no dropped frames during top-bar collapse/expand
animation. No regressions in existing settings page behavior.

**Verification:** Open each settings sub-page, scroll through content with fling gesture — should feel responsive
with no visible frame drops. Verify top bar collapses/expands smoothly. Run unit tests (`CollapsibleTopBarHeightCalcTest`).

## Group B — MusicBrainz improvements

### 6. MusicBrainz search improvements

Two complementary fixes that share the same threshold and the same code path. Both only activate when the initial recording search returns fewer than 3 results — in the common case, nothing changes and no extra API calls are made.

**Problem A — single-word queries miss results.** A user typing "Karrierelied" gets results only where the recording title matches. If the track exists under a different recording name on an album by that artist, recording-only search misses it.

**Problem B — recording search and release search are different indexes.** Recording search looks at track names; release search looks at album names. An obscure track might not match recording search but the enclosing album would match release search.

**Fix A — smart broadening:** When the query is a single word with no Lucene syntax and no UUID pattern, broaden to search across recording, alias, and artist fields: `recording:"Karrierelied" OR alias:"Karrierelied" OR artist:"Karrierelied"`. Existing multi-word searches, UUID lookups, and quoted searches pass through unchanged.

**Fix B — two-stage search with release fallback:** Run the recording search first. If results ≥ 3, return immediately. If < 3, run a release search with the same query and merge results (deduplicate by recording MBID, recording results take priority). Release results are converted to `MetadataSearchResult` using the same DTO mapping — the recording ID comes from the release's first track.

**Combined flow:**
1. Run narrowed recording search
2. If results ≥ 3 → return
3. If results < 3 → run broadened recording search (fix A)
4. If still < 3 → run release search (fix B) and merge

This costs at most 3 API calls in the worst case (single-word obscure track), 1 call in the common case. Combined with the token bucket (item 2), this is a burst of 3 tokens from the 5-token capacity — safe within MusicBrainz's rate limit.

### 7. Album metadata fetching

**Problem:** Fixing metadata for an entire album currently requires editing each track individually from the TrackInfoSheet. If an album has the wrong album artist, year, or genre, the user must repeat the same MusicBrainz search and tag application 12 times.

**Fix:** Add an album-level metadata fetch that applies metadata to all tracks in an album at once.

**API:** MusicBrainz `/ws/2/release/{release-id}?fmt=json&inc=recordings+artist-credits+tags+genres+labels`

This single call returns:
- Release date (year)
- Artist credit (album artist)
- Tags and genres
- Cover Art Archive ID (auto-included in every release response)
- Track listing with recording IDs

**Flow:**
1. User is on the Albums tab, long-presses an album → "Fetch album metadata" option
2. App searches `/ws/2/release?query=release:{albumName} AND artist:{albumArtist}` to find matching releases
3. Shows results in a dialog — user picks the correct release
4. App does ONE release lookup for the full metadata
5. Batch-applies to all tracks in the album: album artist, year, genre
6. Optionally fetches cover art from Cover Art Archive and applies it to all tracks

**What gets updated per track:** album artist, year, genre
**What does NOT get updated:** individual track titles, track numbers (no per-track recording matching without acoustic fingerprinting — v2.0)

**UI:** A new "Fetch album info" context menu item on the album playlist view. Reuses the existing search result dialog pattern from TrackInfoSheet.

**No individual track matching.** This is the key scoping decision. Without acoustic fingerprinting, matching tracks within a release to their MusicBrainz recordings by track number is unreliable (tracks are often numbered differently, have bonus tracks, or are missing numbers entirely). The batch-apply approach covers the most common use case: an entire album with incorrect or missing album-level metadata.

## Group C — New infrastructure

### 8. SAF sidecar .lrc auto-discovery

**Problem:** Users who place `.lrc` files next to their audio files see "No lyrics found" because no code path probes the audio file's parent directory for a sibling `<basename>.lrc`.

**Approach (revised from the June 8 spec based on 2026-06-15 research):**

The original spec proposed using `DocumentFile.listFiles()` to walk the tree. This was wrong — `listFiles()` issues N+1 ContentResolver queries and becomes unusable beyond a few hundred files (one library reported 48 seconds for a large listing).

The correct approach skips `DocumentFile` entirely for lookup. A single targeted `ContentResolver.query()` hits the file directly:

```kotlin
// One query, no tree walk:
val childUri = DocumentsContract.buildChildDocumentsUriUsingTree(treeUri, rootDocId)
val cursor = contentResolver.query(
    childUri,
    arrayOf(DocumentsContract.Document.COLUMN_DOCUMENT_ID),
    "${DocumentsContract.Document.COLUMN_DISPLAY_NAME} = ?",
    arrayOf("$basename.lrc"),
    null
)
```

**Flow:**
1. User picks a folder via `ACTION_OPEN_DOCUMENT_TREE` (one-time)
2. Tree URI is persisted to SharedPreferences
3. `takePersistableUriPermission()` is called with `FLAG_GRANT_READ_URI_PERMISSION`
4. On lyrics load: read tree URI from prefs → build child URI → query for `<basename>.lrc` with display name filter → if found, open InputStream via ContentResolver → decode (UTF-8 → ISO-8859-1 fallback, reusing the existing `decodeLyrics()` helper) → parse as LRC via `String.toSyncedLyrics()` → cache via `LyricsRepository.insertLyrics()`
5. Sidecar check runs before LRCLIB fallback: cache → embedded tag → sidecar .lrc → LRCLIB

**Charset handling:** Reuses the existing `decodeLyrics()` function that tries UTF-8 first, falls back to ISO-8859-1 — same logic as the manual LRC import.

**Dependency:** No new Gradle dependency needed. The `DocumentFile` library (`androidx.documentfile:documentfile`) is NOT required — we use `ContentResolver.query()` and `DocumentsContract` directly.

**Edge cases:**
- Permission revoked: if the tree URI query returns empty or throws `SecurityException`, fall through to LRCLIB. No crash, no prompt — the sidecar path silently degrades.
- Folder contains nested subfolders: we only query for `<basename>.lrc` directly, so we don't need to walk the tree. If the .lrc file is in a subfolder, it won't be found — this is acceptable. Users who organize music into subfolders should place .lrc files alongside the audio file in the same subfolder (which is the standard convention). Adding recursive tree walking would require the expensive `DocumentFile.listFiles()` approach and is out of scope.
- Multiple files with the same basename: Display Name query returns exactly one cursor row. If somehow two files exist with identical names (which the filesystem prevents), the first match wins.

### 9. Per-tab sort memory

**Problem:** All playlist-type tabs (Albums, Artists, Genres, Folders, Playlists) share one `playlistSort`/`playlistSortOrder` preference. Switching from Albums sorted by Year to Artists carries the sort choice over. Each tab should remember its own sort independently.

**Fix:** Replace the single `playlistSort`/`playlistSortOrder` SharedPreferences keys with per-tab keys:

```kotlin
// Settings.kt — replace:
var playlistSort: PlaylistSort
var playlistSortOrder: SortOrder

// With:
var albumSort: PlaylistSort       // "album-sort-key" / "album-sort-order-key"
var artistSort: PlaylistSort      // "artist-sort-key" / ...
var genreSort: PlaylistSort
var folderSort: PlaylistSort
var playlistSort: PlaylistSort    // saved playlists tab, keeps existing key name
var trackSort: TrackSort          // unchanged, already per-tab (Tracks tab only)
```

Each tab pair reads its own pref. The sort button on each tab changes only that tab's preference. Defaults: Albums → Title, Artists → Title, Genres → Title, Folders → Title, Playlists → Title.

**Impact:**
- PlayerScreen.kt: pass per-tab sort to each `TabContent` call
- PlayerViewModel.kt: expose per-tab sort flows
- SortButton.kt: no changes — the button already accepts sort/order parameters generically

**Migration:** Existing `playlistSort`/`playlistSortOrder` keys stay for the Playlists tab. Albums/Artists/Genres/Folders get new keys with default Title ascending, so existing users get a clean start on those tabs.

## Group D — Import improvements

### 10. M3U relative path import

**Problem:** M3U playlist import only handles absolute track paths (lines starting with `/`). When an M3U file uses paths relative to its own location — the default export format from VLC, foobar2000, and most desktop players — every entry is silently dropped and the user imports an empty playlist.

**Context:** The M3U importer lives in `MainActivity.kt` (which reads the file via SAF `OpenDocument` and extracts the playlist name) and `PlayerViewModel.kt` (which parses the file content and matches paths against the track list). The URI from an SAF document picker is a `content://` URI, not a filesystem path — but the track list stores filesystem paths from MediaStore. So we need to map from `content://com.android.externalstorage.documents/document/primary%3AMusic%2Fplaylist.m3u` to `/storage/emulated/0/Music` (the M3U file's parent directory).

**Fix:** Three changes across two files.

**1. Extract a shared URI parser (MainActivity.kt):** The existing `getPathFromFolderUri` parses SAF `tree/` URIs. The M3U picker receives `document/` URIs. Both share the same format — the only difference is the path prefix. Extract a helper that takes the prefix as a parameter, then use it from both call sites.

```kotlin
// Shared — no duplication:
private fun extractStoragePath(uri: Uri, schemePrefix: String): String {
    val decoded = Uri.decode(uri.toString())
    val sd = decoded.substringAfter("$schemePrefix/").substringBefore(':')
        .takeIf { it != "primary" } ?: "emulated/0"
    val path = decoded.substringAfterLast(':')
    return "/storage/$sd/$path"
}

// Refactored to call the helper:
private fun getPathFromFolderUri(uri: Uri): String =
    extractStoragePath(uri, "tree")

// New — extracts parent directory from a document URI:
private fun getDirectoryFromDocumentUri(uri: Uri): String =
    File(extractStoragePath(uri, "document")).parent
```

**2. Plumb the directory through the picker channel (MainActivity.kt):** The existing `pickedPlaylistChannel` carries a `Pair<String, String>` (name, content). Change it to carry the directory as a nullable third element.

```kotlin
// Channel type change:
val pickedPlaylistChannel = Channel<Triple<String, String, String?>>()

// In the picker callback — capture directory alongside name and content:
val m3uDirectory = getDirectoryFromDocumentUri(it)
// ... send Triple(name, content, m3uDirectory)
```

**3. Resolve relative paths in parseM3U (PlayerViewModel.kt):** Move path resolution to `Dispatchers.IO`, resolve relative paths against the M3U's parent directory, and filter comment lines.

```kotlin
fun parseM3U(playlistName: String, fileContent: String, m3uDirectory: String?) {
    viewModelScope.launch {
        val tracks = withContext(Dispatchers.IO) {
            fileContent.lines()
                .filter { it.isNotBlank() && !it.startsWith("#") }
                .map { line ->
                    when {
                        line.startsWith("/") -> line
                        m3uDirectory != null -> runCatching {
                            File(m3uDirectory, line).canonicalPath
                        }.getOrNull()
                        else -> null
                    }
                }
                .filterNotNull()
                .mapNotNull { path -> _trackList.value.fastFirstOrNull { path == it.data } }
        }
        val name = playlistName.filter { it.isDigit() || it.isLetter() || it.isWhitespace() }

        playlistRepository.insertPlaylist(Playlist(name = name, trackList = tracks))
        SnackbarController.sendEvent(SnackbarEvent(message = R.string.imported_successfully))
    }
}
```

**Thread safety:** Path resolution uses `withContext(Dispatchers.IO)` — `File.canonicalPath` does filesystem I/O (resolves `.` and `..`, normalizes separators, strips symlinks) and should not run on the main dispatcher.

**Error handling:** `runCatching` wraps each path resolution. A malformed relative path in a playlist doesn't crash the import — the bad entry is dropped.

**Comment filtering:** Lines starting with `#` (EXTINF metadata, header directives) and blank lines are filtered. The existing code only kept lines starting with `/`, which incidentally filtered comments but also dropped all relative paths. The new filter is explicit.

**Backward compatibility:** If `m3uDirectory` is null (URI parsing failed for any reason), the importer falls back to absolute-path-only matching — exactly the current behavior. No regression.

**No new dependencies.** Uses only `java.io.File` and `kotlinx.coroutines.withContext`.
